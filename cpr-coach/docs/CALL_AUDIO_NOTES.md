# Call Audio Routing Notes (`USAGE_MEDIA` ↔ `USAGE_VOICE_COMMUNICATION`)

## Pitfalls
- **Track & manifest (`AudioEngine.kt:25,346-373`, `MetronomeService.kt:87`):** `MetronomeService` builds `AudioEngine(this, USAGE_VOICE_COMMUNICATION)` once, and `openTrack()` binds `usage` per `AudioTrack`. Switching mid-session must reopen the `AudioTrack` inside `AudioEngine` while preserving `phase`, cached `clips`, `voiceMuted`, and `clipDone`. `AndroidManifest.xml` also lacks `MODIFY_AUDIO_SETTINGS`, which `AudioService` requires for `setCommunicationDevice()` and `setSpeakerphoneOn()`.
- **Call detection without permissions:** Without `READ_PHONE_STATE`, `TelephonyManager` is unavailable. `addOnModeChangedListener` requires API 31+, so API 30 (`minSdk = 30`) must poll `audioManager.mode`. `ACTION_DIAL` only opens the dialer; `mode` reaches `MODE_IN_CALL` only after the user dials.
- **Self-induced mode changes:** Never call `audioManager.mode = MODE_IN_COMMUNICATION`. If our app sets mode—or if our `USAGE_VOICE_COMMUNICATION` track / `HandsFreeController` (`AudioSource.VOICE_COMMUNICATION`) triggers `MODE_IN_COMMUNICATION`—treating `MODE_IN_COMMUNICATION` as a phone call latches onto our own audio and never returns to `USAGE_MEDIA`. Check `MODE_IN_CALL` for cellular calls.
- **Dispatcher routing:** `USAGE_VOICE_COMMUNICATION` shares the call route and `STREAM_VOICE_CALL` volume. In `AudioDeviceBroker.topCommunicationRouteClient()` ([AOSP `385ca73d1a95`](https://android.googlesource.com/platform/frameworks/base/+/385ca73d1a95%5E%21)), when Telecom owns `mAudioModeOwner` (`MODE_IN_CALL`), `AudioService` ignores route requests from non-owner UIDs without `MODIFY_PHONE_STATE` (and from idle UIDs without active playback/recording), or Telecom overrides the route back to earpiece/Bluetooth. When accepted, it pulls the dispatcher onto the loudspeaker, and 110 BPM clicks/clips can mask the dispatcher or bleed into the call mic.
- **Restoring state:** On API 31+, use `clearCommunicationDevice()`, not `setCommunicationDevice(previous)`. On API 30, calling `setSpeakerphoneOn(false)` when Emergency stops during an active call turns off a speakerphone the user enabled in the dialer; restore only when `mode == MODE_NORMAL`.
- **Oppo / Realme:** Repo M0 notes on Realme `RMX3392` (`MetronomeService.kt:86`, `docs/STATUS.md`) show `USAGE_MEDIA` stopped during a call while `USAGE_VOICE_COMMUNICATION` played; connected-call audio remains unverified by ear. No other Oppo/Realme quirk is claimed without a vendor source.

## Phone Test (Call a Teammate — Never 112)
1. Enter Emergency; verify `USAGE_MEDIA` plays beat and steps on the loudspeaker.
2. Tap Call 112, replace `112` with a **teammate's number**, and call. On API 30 and 31+, verify switching to `USAGE_VOICE_COMMUNICATION` drops no beat/clip and check whether speakerphone enables automatically or requires the dialer button.
3. Confirm both teammate and coaching are clear on speaker, the teammate hears the rescuer over the beat, and whether `HandsFreeController` is silenced (`isClientSilenced`).
4. Hang up during Emergency (verify return to `USAGE_MEDIA` on speaker); repeat and hold Stop mid-call (verify the call stays on speaker).
