# Elbow latency sweep

Run `python tools/elbow_sweep.py` from the `cpr-coach` directory. The script replays recordings 10–15 through a Python port of `LandmarkGuard.check`, then the elbow part of `PostureJudge`. It reports every sustain (0.4–1.0 s), median window (0.6–1.0 s), and fast-path margin (0–15 degrees) combination. `CPR_DATA_DIR` can point to another copy of `tools/testdata`.

The elbow limit is the Kotlin fallback `145°`; clear uses its `153°` hysteresis threshold. A median below `145° - margin` shortens the pending bent sustain by 0.3 s, with a 0.2 s floor. The fast duration is fixed when the sustain starts. The median must span 600 ms. Bent share counts sampled reads in each labelled bent segment. False reads count bent samples on presumed straight spans: all of 10, 11, and 13; 12 before 18 s; 14 from 3–24 s; and only the `straight` labels for 15. Recording 10–13 spans use the Kotlin comments' straight-pushing context, not independent labels. The 12 bent and 15 block labels come from `labels.csv`.

The default sweep found no zero-false setting that detected all three labelled bent blocks. All six 0.6 s median-window settings per sustain had zero false samples, but detected none of those blocks. The best observed false count among settings that detected the first 15 block and 12 block was 20 samples, at sustain 0.8 s, window 0.7 s, margin 15°: delays were 0.64 s (12), 0.67 s (15 block 1), and no read (15 block 2); shares were 95%, 87%, and 0%. At 0.4 s sustain, 0.7 s window, 0° margin, delays were 0.07 s, 0.18 s, and 7.38 s, with shares 91%, 97%, and 2%, but 107 false straight samples. No fastest zero-false setting or positive margin exists for all three blocks.

Port check: measured 1 s elbow-median ranges in the replay were 141–179° (10), 170–179° (11), 155–171° (12 before 15 s), 128–174° (13), 173–179° (14 straight), 124–144° (15 bent block 1), and 142–171° (15 bent block 2). The median values for blocks 1 and 2 of 15 were 135° and 152°, consistent with the Kotlin comment's 124–144° and median 151° for block 2. The full-file minima for 10 and 13 (141° and 128°) do not match the Kotlin comment's 165–178° straight-pushing range; those minima include all recorded frames, not a separately labelled pushing-only interval. The CSV has no image aspect field, so the guard port uses aspect 1.0; this can affect which frames it filters. No Android build or Gradle tests were run; this analysis needs only Python.
